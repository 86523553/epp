## 二、用户抱怨的现象

拖动组件时：**很慢、跟不上鼠标、有残影**（早期版本还有彩色条纹、拖到哪黑到哪）。

## 三、已定位的真实原因（都有实测依据）

| # | 原因 | 证据 | 处置 |
|---|---|---|---|
| 1 | 拖动期间每帧**整窗重绘** | `IDE_DBG_FPS=1` 实测整窗 `[paint] 28.9 ms`，画布单独 `10.3 ms` | 改成底图缓存 + 脏矩形 |
| 2 | 脏矩形**一路累加**（拖多远算多远），最终等于整张画布，还会越界读位图 → 彩条 | 用户截图里的紫蓝条纹；日志 `dirty=` 逐帧变大 | 改成每帧只算「上一帧位置 ∪ 这一帧位置」，并裁到画布内 |
| 3 | 从底图 `BitBlt` 时**没裁到画布**，源坐标越界 → 读到未初始化内存 = 黑块 | 用户「拖到哪黑到哪」 | 同上，已裁 |
| 4 | **GDI+ 延迟提交**：从同一个 DC `BitBlt` 抓底图前没 `GdiFlush()`，抓到的是还没画上去的内容（全黑） | 黑块现象 | `cvs_base_capture()` 开头已加 `GdiFlush()` |
| 5 | 拖组件时 `g_cvsBaseOn` 竟然是 false → 每帧退化回整画布重绘 | 拖动日志 `NO_BASE -> 走整画布重绘` | 未完全解决；最后一版加了「自愈式底图」（见下） |

## 四、当前实现（`main.cpp` 里的关键符号）

- `g_cvsBaseDC / g_cvsBaseBmp / g_cvsBaseW/H / g_cvsBaseOn / g_cvsBaseCanvas`：画布底图（**不含**被拖组件的画布快照）
- `cvs_base_capture(HDC src, int ox, int oy)`：抓底图（已加 `GdiFlush`）
- `g_dragPrev / g_dragDirty / g_dragDirtyOn`：脏矩形（每帧重算）
- `drag_paint_screen(HWND)`：拖动时**直接往屏幕 DC 上画**（贴底图那块 + 补画被拖组件），不经过 `InvalidateRect`/`WM_PAINT`；
  组件用 GDI+ 画，所以先画进一张小的离屏位图再 `BitBlt` 上屏（避免 GDI+ 直接画屏幕又慢又留半成品像素）
- `paint()` 开头的快速路径：`g_cvsBaseOn && (drag==DMove||DResize)` → 只贴脏矩形 + `paint_ctl_layer(dc, true)`
- `paint()` 新增「自愈式底图」分支（**未编译验证**）：拖动开始那帧若底图不存在，就现场画 `paint_canvas` → 抓底图 → 补组件
- `paint_ctl_layer(HDC, bool onlySel)`：控件 + 悬停 + 选中框 + 窗体边框；`onlySel=true` 只画选中的
- 拖动时 `g_hideDragCtl=true`：抓底图那一帧不画被拖组件本体**和它的选中框**（不跳过选中框会留下蓝框残影）
- 松手才吸附到网点：拖动过程自由跟手（`on_lbutton_up` 里做吸附 + 边界钳制）
- 拖动/改大小都钳制在窗体客户区内：`[0, cw-w] × [0, (ch-caption)-h]`

## 六、还没解决的问题 / 下一步建议

1. **先编译部署带「自愈式底图」的版本**，再用夹具跑一次真实 `drag=1`，看日志是不是 `DIRECT 0.x ms`。
   如果是 → 慢/残影应当消失，交给用户手感确认。
   如果仍是 `NO_BASE` 或 `FULL xx ms` → 说明底图抓取还有别的失败分支（在 `cvs_base_capture` 里已有诊断日志，直接看日志）。
2. **框选（DMarquee）目前仍是整画布重绘**，也是慢的。可参照 `drag_paint_screen` 的写法用底图 + 只画虚线框。
3. **彻底方案（用户明确提过"它不能自然处理吗"）**：把设计器里的每个组件做成**真实子窗口**（BUTTON/STATIC/EDIT），
   拖动只 `SetWindowPos`，由系统搬像素，零重绘 —— 这正是易语言设计器的做法（参考 `参考\ycIDE\VisualDesigner.cpp`：
   它的设计器是独立子窗口，拖动只让该子窗口失效）。工作量大但一次到位。
4. 参考实现：`参考\ycIDE\`（C++，MIT）。它的 `VisualDesigner` 是**独立子窗口**，这是它拖动不卡的结构性原因；
   我们的设计器是把所有组件画在同一个大窗口上，这是所有卡顿的总根源。

## ✅ 2026-11-09 00:15 结案：真凶已找到并修复

按第六节建议执行时，用 `IDE_TEST_DRAG=1` 离线渲染器复刻真机时序（先画普通帧再进入拖动），
拖 5 帧的渲染图上残留 **5 个按钮影像**——底图从未真正生效。两个 bug：

1. **`cvs_base_capture` 抓完底图把位图摘了**（`SelectObject(g_cvsBaseDC, ob)` 还原默认位图）。
   之后每帧贴底图的 BitBlt 从 1×1 单色占位位图取源 = 无效操作，上一帧影像永远擦不掉。
   修复：位图保持选中（cvs_base_free 成对回收）。**这一行就是"拖动慢/残影/不同步"的真凶。**
2. **`paint()` 自愈式底图分支污染底图**：画隐身画布→抓底图→又把组件画回背缓冲才返回，
   WM_LBUTTONDOWN 紧接着二次抓底图，底图带旧影像。该分支已删除，底图只在
   WM_LBUTTONDOWN 抓一次；中途丢底图走整画布快速路径兜底。

修复后离线实测：**拖动帧平均 0.11 ms / 最差 0.13 ms**（普通帧 29.7 ms，起手帧 19.0 ms 一次性）。
框选也补了虚线框并接入同一条快路径（以前没画虚线框还整画布重绘）。

复验方法：`set IDE_TEST_DRAG=1 && ide.exe --screenshot out.png --light proj_test.e`
看 `%LOCALAPPDATA%\hermes\cache\scratch\drag_mid.png` 应只有 3 个组件、无残影，
stderr 打印 [drag-test] 三行耗时。`ide.exe` 已部署修复版。
