# 方案：epp 单文件支持库（`.epp`）

> 定位：**一个文件 = 一套支持库**。中文用户不需要看 `.h`，双击看包就知道有什么；IDE 加载时同时拿到“给人看的中文清单”和“给编译器看的头文件/静态库”。
> 生成器：`开发环境\工具\pack_epp.py`（唯一打包入口）

## 1. 为什么改（原方案为什么不合适）

| 原做法 | 问题 |
|---|---|
| 散目录 `核心支持库.elib` + `组件库\include\*.h` + `静态库\*.a` | 用户要认识三种文件；拷给别人容易漏；查看器要分别解析两套格式 |
| ycIDE / 易语言的 `.fne` | 二进制 DLL，必须逆向才能看内容，中文用户完全看不懂 |
| su-lang 的 `.sulib`（JSON 指向磁盘散文件） | 只是清单，删了目录就失效，不能单独分发 |

`.epp` 的取舍：**用 zip 容器 + 中文清单**，既是一个文件（好分发），又是可读文本（好做查看器）。

## 2. 包内结构（固定）

```
核心支持库.epp                 （zip，deflate 压缩）
├── manifest.json     中文元信息：名称/版本/统计/文件索引
├── 命令.txt          中文命令表   @分类 / @命令 / 英文名= / 返回= / 说明= / 参数=
├── 组件.txt          中文组件表   @公共事件 / @公共方法 / @组件 / @属性 / @事件 / @方法
├── include/*.h       给编译器（组件头 + 公共事件/公共方法）
└── lib/*.a | *.lib   静态库（可选）
```

**双份数据是刻意设计**：`命令.txt` / `组件.txt` 是**唯一真源**（IDE 属性框、支持库页、查看器都读它），`include/` 只是给编译器用。以后再也不用从 `.h` 反解析属性。

### 2.1 `manifest.json` 示例

```json
{
  "格式": "epp",
  "格式版本": 1,
  "生成器": "pack_epp.py",
  "名称": "核心支持库(全量)",
  "版本": "5.7.64",
  "统计": {
    "命令": 688, "分类": 24, "组件": 42,
    "属性": 710, "事件": 63, "方法": 0,
    "公共事件": 13, "公共方法": 295
  },
  "文件": { "命令表": "命令.txt", "组件表": "组件.txt" }
}
```

### 2.2 `组件.txt` 片段（实际输出）

```
# ===== 公共事件（全部组件共享，共 13 条）=====
@公共事件 13
@事件 鼠标左键被按下
说明=用户在本组件上按下鼠标左键时触发。
...
# ===== 公共方法（全部组件共享，共 295 条）=====
@公共方法 295
@方法 取窗口句柄|整数型
说明=取出本窗口或窗口组件的窗口句柄（即HWND）
...
@组件 标签
文件=label.h
英文名=label
属性数=29
@属性 左边
类型=整数型
@属性 标题
类型=文本型
...
```

## 3. IDE 侧要接的三处（main.cpp）

### 3.1 加载（替换现有 elib + 组件目录扫描）

```
打开 库.epp
  → 读 manifest.json 填“支持库页”标题与统计
  → 读 命令.txt  → 命令提示 / 支持库页
  → 读 组件.txt  → 组件箱、属性框、事件列表、方法列表
  → 把 include\ + lib\ 解压到 %LOCALAPPDATA%\epp\lib\<名称>-<版本>\（按版本目录，避免冲突）
  → 编译时把这个目录加进 include 路径、把 lib\*.a 加进链接参数
```

要点：
- 解压目录按 `名称-版本` 命名，多个库并存不打架；已存在则跳过解压（比对内嵌 sha256）。
- 组件箱只看 `组件.txt` 的 `@组件` 段，**不再扫头文件**，加载速度从“解析 43 个 .h”变成“读一个文本”。

### 3.2 属性框/事件列表（补上现在缺的）

```
选中组件 → 属性行 = 组件.txt 里该组件的 @属性
         → 事件列表 = @公共事件 + 该组件的 @事件
         → 方法列表 = @公共方法 + 该组件的 @方法
         → .e 里带来但表中没有的属性，继续走现有「源码属性」组
```

这正好补掉现在“事件只有 1 条”的问题：公共事件 13 条对所有组件生效。

### 3.3 查看器（以后做独立小工具）

```
打开 .epp → 读 manifest.json
  → 左侧树：命令分类 / 组件列表 / 公共事件 / 公共方法
  → 右侧：选中项的中文说明、参数表、示例
  → 全程不需要 .h，也不需要反编译
```

## 4. 打包命令（唯一入口）

```powershell
cd "<仓库根>\开发环境\工具"

# 打现有库（237 命令 / 675 属性 / 5 方法）
C:\Python314\python.exe pack_epp.py --name 核心支持库 `
  --elib ..\..\运行环境\核心支持库\核心支持库.elib `
  --comp-dir ..\..\运行环境\组件库\核心组件库\include `
  --static-dir ..\..\运行环境\静态库 `
  --out ..\..\运行环境\核心支持库.epp

# 打全量库（688 命令 / 710 属性 / 13+63 事件 / 295 方法）
C:\Python314\python.exe pack_epp.py --name "核心支持库(全量)" `
  --elib out_krnln\核心支持库.elib --comp-dir _pack_hdr `
  --out out_krnln\核心支持库.epp

# 查看
C:\Python314\python.exe pack_epp.py --list  x.epp
C:\Python314\python.exe pack_epp.py --dump  x.epp 命令
C:\Python314\python.exe pack_epp.py --dump  x.epp 组件
```

`--list` / `--dump` 就是**查看器的命令行原型**，以后 GUI 查看器直接复用同一套解析。

## 5. 与旧格式的关系

| 旧物 | 处置 |
|---|---|
| `.elib` | 保留为**打包源**（`--elib`），不再直接给 IDE 分发 |
| `组件库\include\*.h` | 保留为**打包源**（`--comp-dir`） |
| `.sulib` | 编译期清单（include/源码/链接参数），可与 `.epp` 并存；`.epp` 内不再放 sulib |
| `_弃用_slib\` | 早期 `.slib` 试点（同格式旧后缀），仅供对照 |

## 6. 已知限制

1. **静态库体积**：现在 `libcore_support.a` 447 KB 会整个进包，打包后约 235 KB（压缩后）。将来命令补到 688 条，静态库会变大，必要时拆“核心 + 扩展”两个 `.epp`。
2. **公共方法归属**：295 条方法挂在“公共”段（易语言设计如此），不逐组件复制，避免 `组件.txt` 涨到 1.2 万行。
3. **事件参数**：`按下某键(键代码)`、`字符输入(字符代码)`、`反馈事件(参数一,参数二)` 的参数暂未写入（fne 未导出参数表），标为待补。
4. **加密**：`.epp` 明文可解压。若将来要防抄，加一层简单混淆即可（不影响查看器，因为查看器读的是解密后的内存）。
5. **版本兼容**：`manifest.json` 带 `格式版本`，IDE 读到未知版本要拒绝加载并提示升级。

## 8. 落地定稿：一个支持库文件 + 一个静态库文件（2026-11-08）

用户要求「支持库一个文件、静态库一个文件」，于是最终形态定为：

```
环境\核心支持库\核心支持库.epp      ← 支持库：就这一个（377 KB，stored zip）
环境\静态库\libcore_support.a      ← 静态库：就这一个（+ include\ 头文件）
工具\_打包源\核心支持库\*.elib *.sulib   ← 只作打包源，不再进 环境\
```

### 8.1 为什么用 stored（不压缩）

压缩包里 C++ 要自己实现 inflate；stored 只需读中央目录 + 偏移取字节，`main.cpp` 里 `epp_zip_entry()` 约 60 行，无外部依赖。
代价：377 KB vs 240 KB，本地工具无所谓。

### 8.2 IDE 侧改动（已实现）

| 位置 | 改动 |
|---|---|
| `read_bin_file()` | 二进制整文件读（上限 64 MB） |
| `u8_to_w()` | 包内 UTF-8 文本转宽字符 |
| `epp_zip_entry(zip, 条目名, out)` | 解析 EOCD → 中央目录 → 本地头，取 stored 数据 |
| `lib_parse_text()` | 从「读文件 + 解析」拆成「解析文本」，`lib_parse_elib` 变成薄壳 |
| `lib_parse_epp()` | 取包内 `命令.txt` 走同一套解析，再用 `manifest.json` 覆盖名称/版本 |
| `libs_scan()` | **先扫 `*.epp`，没有再退回 `*.elib`** |

### 8.3 验证

- `pack_epp.py --store` 产出 377.9 KB，`--list` 统计 237 命令 / 42 组件 / 675 属性 / 53 事件 / 5 方法
- 把 `.elib`/`.sulib` 移走后重编译，`ide.exe --shot-lib` 截图显示「核心支持库 1.0 · 237 条」，无报错
- 即：**IDE 现在真的只靠一个 `.epp` 就能列出全部命令**

### 8.4 后续（组件属性/事件也走 .epp）

`组件.txt` 已经打进包里（42 组件 / 675 属性 / 53 事件 / 5 方法），但 IDE 目前仍从 `环境\组件库\核心组件库\include\*.h` 解析属性。
下一步把 `comp_scan()` 也改成「优先读 `.epp` 的组件.txt」，那时 `环境\组件库\` 整个目录都可以不要。

## 9. 定稿执行：头文件进包，环境只剩 2 个文件（2026-11-08）

按「一个支持库 + 一个静态库」定稿，`include/` 目录塞进 `.epp`：

```
环境\核心支持库\核心支持库.epp     493 KB（61 个头文件在里面）
环境\静态库\libcore_support.a     447 KB
工具\_打包源\静态库头\*.h         18 个实现头，只作打包源
```

### 9.1 打包

`pack_epp.py` 新增 `--inc-dir`（可重复），把核心库实现的 18 个 `.h` 一并写进包内 `include/`；
遇到重名头文件跳过并打印提示（现为 43 组件头 + 18 实现头 = 61 个，无重名）。
打完自动 `rmtree(_pack_tmp)`，不在 `环境\` 留中间目录。

### 9.2 IDE 侧（已实现）

| 步骤 | 实现 |
|---|---|
| 启动扫库 | `libs_scan()` 找到 `.epp` 后调 `epp_extract_include()` |
| 解压位置 | `%LOCALAPPDATA%\epp\lib\lib<N>\include\`（**ASCII 路径**，避免 MinGW 中文路径问题） |
| 编译参数 | `build_compile_run()` 里加 `-I"<缓存目录>"`，F7 生成的 g++ 命令行自动带上 |
| 建目录 | 新增 `mkdirs_w()` 逐层建目录 |

### 9.3 踩坑（重要）

`CreateDirectoryW()` **只建最后一层**，父目录不存在直接失败且不报错。第一次实现时 `lib0\include` 建不出来 → 每个头文件 `CreateFileW` 也全失败 → 函数返回 false、缓存目录空。改成逐层 `mkdirs_w()` 后 61 个头文件全部落地（`text.h` 18807 B 与源文件字节一致）。

### 9.4 验收

| 项 | 结果 |
|---|---|
| `核心支持库.epp` | 493.4 KB / 64 条目 / 61 头文件（stored） |
| `环境\静态库\` | 只有 `libcore_support.a` |
| 删缓存后启动 IDE | `%LOCALAPPDATA%\epp\lib\lib0\include` 生成 61 个 `.h` |
| `--shot-lib` | 「核心支持库 1.0.0 · 237 条」，无报错 |

## 10. 组件库也进包：`环境\组件库` 取消（2026-11-08）

`.epp` 的 `include/` 里本来就有 43 个组件头，组件箱没必要再从 `环境\组件库\` 读一遍。

### 改动
- 新增 `libs_prepare_epp_cache()`：启动时把 `.epp` 的 `include/*.h` 解到 `%LOCALAPPDATA%\epp\lib\libN\include`，同时填 `g_libIncDir`（编译 `-I`）和 `g_compIncDir`（组件解析）。
- `app_init()` 里在 `comps_load()` 之前先调它（否则组件扫描时缓存还没生成）。
- `comps_load()` 增加第 0 支路：`g_compIncDir` 有值就直接扫该目录 `*.h`，跳过 `环境\组件库\`；解析函数仍是原来的 `comp_parse_header()`，一行没改。
- 核心实现头（text.h 等 18 个）没有 `// @component` 注解，解析器自动忽略，不会污染组件箱。

### 验证（把 `环境\组件库` 整个移走 + 删缓存后启动）

| 项 | 结果 |
|---|---|
| 输出面板 | 「组件库清单：核心组件库（42 个组件，.epp 包内头文件）」「已加载 1/1 个支持库」 |
| 组件箱 | 42 个组件正常（影像框/按钮/选择框/选择列表框/客户/颜色选择器/组合框/通用对话框…） |
| 属性面板 | 正常，编辑框：名称/类型/左边/顶边/宽度… |
| 缓存 | 61 个头文件落地 |

### 现在的 环境\ 只跟库有关的两项
```
核心支持库\核心支持库.epp     493 KB   ← 支持库（唯一）
静态库\libcore_support.a      447 KB   ← 静态库（唯一）
```
