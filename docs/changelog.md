## 2026-11-09 00:35 拖动改成「影子窗口」方案（业界标准做法，彻底解决跟不上鼠标）
用户反馈：修掉底图 bug 后好了一些，但拖快了鼠标还是跑出去老远。按用户要求先调研国内外资料再动手。

### 调研结论（取舍依据）
- 微软 WinForms 设计器（BehaviorService.AdornerWindow）：设计器 UI 画在一个独立透明层上，
  拖拽预览是「控件截图 + 跟随鼠标的预览」（Control.DrawToBitmap 缓存一张图）。
- 多篇中英文资料一致结论：需要系统级顺滑的拖动视觉，用 **顶层 WS_EX_LAYERED 小窗 +
  UpdateLayeredWindow**；主窗口拖动期间完全不重绘，窗口移动由 DWM 合成。
- 直接往窗口 DC 上 BitBlt（我们原来的 drag_paint_screen）绕开 WM_PAINT，
  DWM 的呈现时机不受控，高频更新会被合并/延后 —— 这就是"帧耗时 0.2ms 却仍然跟不上"的原因。

### 实现（源码/main.cpp，全通用，无组件特例）
- 拖动开始（第一次真的移动）把控件按当前缩放画进 32bpp DIB：窗体底色判透明、其余 alpha=255
  （预乘 alpha），控件描一圈 accent；交给 WS_EX_LAYERED|TOOLWINDOW|NOACTIVATE|TRANSPARENT|TOPMOST
  的影子窗口 UpdateLayeredWindow 上屏（92% 不透明，一眼看出是拖动预览）。
- 之后每次 WM_MOUSEMOVE 只 SetWindowPos(SWP_NOREDRAW) 挪影子，**画布零重绘**；
  改大小（DResize）才重画影子内容。松手/捕获被抢先收影子再重绘画布落位。
- 按下不再立刻隐身+抓底图：单击不闪、起步不白付一次整画布重绘；动了才隐身→抓底图→举影子。
  框选（DMarquee）没有影子，仍走底图+虚线框；底图路径保留为兜底。
- WM_MOUSELEAVE 拖动中不再整窗重绘；新增 WM_CAPTURECHANGED 收尾（Alt+Tab/弹窗抢鼠标不留影子）。

### 自验（IDE_PROBE_DRAG=1 + IDE_PROBE_GHOST=1[+_DROP]）
- 影子移动 12 帧共 2.8ms（每帧 0.23ms，就是一次 SetWindowPos）。
- 截屏验证：影子浮起（蓝边、半透明）、原位置只剩背景；松手后影子收干净、控件落位、

## 2026-11-09 拖动跟手（第三轮：代码审查后定位的四处真问题）
用户反馈"影子方案好一点，但仍然跟不上"。以代码审查方式把拖动链路逐段过了一遍，
找到的不是"模糊的感觉"，是四处可复现的实现问题：

1. **位移被逐步吞掉（根因，最要命）**
   `on_mouse_move` 的 DMove/DResize 分支原来是「`c.x += (mx - dragFrom.x) / (zoom*g_s)`，
   然后把 `dragFrom` 改成当前点」。除以缩放后的**小数部分每帧都被截掉**：
   界面缩放 125%~150% 时，人手每帧只挪 1~2px，`dx` 常算成 0，位移全丢。
   实测 150% 下慢拖 100 步，控件几乎原地不动 —— 用户说的"跟鼠标差很远"就是它。
   **改为绝对定位**：按下瞬间记 `dragFrom0 / dragX0 / dragY0`，每帧
   `c.x = dragX0 + (mx-dragFrom0.x)/(zoom*g_s)`，浮点、不截断、不累加。
   自验：150% 缩放、1px/步拖 100 步，误差 0.00（旧实现误差 = 整个位移）。

2. **消息里的坐标是过期的**
   拖动分支虽然已经把消息队列里的 WM_MOUSEMOVE 吸空，但吸空后用的还是**当前这条消息**
   的 lParam。改为吸空后直接 `GetCursorPos` + `ScreenToClient` 取光标真值 ——
   这是唯一不会过期的坐标源，快速甩动时差的就是这几十毫秒。

3. **每帧 HWND_TOPMOST**
   `ghost_push` 每帧 `SetWindowPos(..., HWND_TOPMOST, ...)`，等于每帧把影子从 z 序里
   摘出来再插回顶部，DWM 每次都要重排图层。改为创建时置顶一次、之后 `SWP_NOZORDER`。
   同时去掉 `SWP_NOREDRAW`（会让分层窗口内容滞后一拍）。

4. **起手同步重绘**
   第一次移动时 `UpdateWindow()` 同步重画一整块画布，正好卡在用户刚出手那一帧。
   改为：按下时**预渲染影子位图但不显示**（只给小控件，≤420×320），第一次移动只
   `ShowWindow` + 落位；擦旧像改成异步 `InvalidateRect`，不再 `UpdateWindow`。

另修一处会放大"不同步"观感的功能缺陷：
- **多选拖动只动 sel[0]**：框选一堆组件再拖，只有一个跟着走。改为按整组包围盒一起走
  （用按下时的 `dragSnapCtl` 快照 + 绝对位移），并以包围盒夹在窗体内。

变更文件：源码/main.cpp（on_mouse_move / WM_MOUSEMOVE / WM_LBUTTONDOWN / ghost_*）。

## 2026-11-09 拖动跟手（第四轮：6 组文献调研后改回"直接上屏"路线）
用户实测影子窗口方案仍"不丝滑"，且反馈"按钮拖到窗体中部就再也无法右移"。

### 调研（6 组主题，约 30 篇）
- Raymond Chen / SO 高票：**WM_MOUSEMOVE 是队列空闲时"现生成"的，坐标永远是最新值**，
  消息本身不会滞后几个身位。位置滞后只可能来自：坐标数学、每帧处理过久、呈现路径。
- 高报告率鼠标（1000Hz）+ 每条消息处理 >1ms 会饿死 WM_PAINT → 拖动帧必须亚毫秒。
- WinForms 设计器源码（BehaviorService）：拖动预览画在常驻透明 AdornerWindow 上，
  是「重绘」不是「移动窗口」。
- 系统 ImageList_DragMove（资源管理器拖文件用了几十年）：LockWindowUpdate +
  在目标 DC 上擦旧画新，直接绘制。
- SO「Can't get rid of jitter」系列：DWM 下 GDI BitBlt 到窗口 DC 是即时更新窗口表面、
  下次合成直接取用；移动窗口要额外过 SetWindowPos 同步路径 + DWM 图层重排。
- 结论：**业界公认跟手正解是「直接绘制上屏」，移动分层窗口反而天生慢一拍。**

### 改动
- 默认路线改回 direct：第一次移动时隐身 → 同步重画 → 抓干净底图 →
  每帧「贴底图 + 画控件」直接上屏（drag_paint_screen）。影子窗口改为
  IDE_DRAG_GHOST=1 时的对照路径。
- DMove 加 CLAMP 诊断日志：触碰窗体边界时把 cw/组右缘/剩余余量记进 IDE_DRAG_LOG，
  用于定位"窗体里明明有空位却拖不动"的问题。

## 2026-11-09 拖动跟手（第五轮：找到根因——坐标缩放错位）✅ 用户确认"丝滑"
用户仍反馈不跟手后，先给 IDE_BENCH_DRAG 加了分段计时（写进 IDE_DRAG_LOG，GUI 无 stderr）：
- 整画布 BitBlt 0.02ms / 只画一个控件 0.07ms / 小脏块 0.075ms / 画布 paint 0.34ms
- **整窗 paint = 18.9ms**（裁到 10x10 也剩 4.2ms = 纯调用开销）
→ 绘制早已不慢，瓶颈一定在别处。

### 根因：ctl_rect() 位置与尺寸用了不同的缩放系数
`ctl_rect` 旧实现：位置 `g_formX + c.x * zoom`（只乘 zoom），尺寸却经 R() 又乘一次 g_s
（= zoom*g_s）。本机 AppliedDPI=144（150%），后果：
- 控件越往右下画得越偏（窗体按 1.5 倍画、控件按 1 倍排）；
- **拖动时鼠标走 1px，控件只走 1/g_s = 0.67px**，拖得越快差得越远。
这就是五轮以来"鼠标跑好远、控件跟不上"的唯一真凶——绘制再快也没用，位移本身就是错的。
改成统一系数 k = zoom * g_s（位置/尺寸/标题条偏移全用 k）。g_s=1 时与旧行为完全一致。

### 配套修复
1. **拖动过程零夹紧**：原 DMove 每帧把位移夹进窗体边界，组件一碰边就停住、
   鼠标还在走（"拖到某个位置就再也拖不动了"）。改为拖动 1:1 跟随（可拖出窗体），
   松手时在 on_lbutton_up 统一吸网点+收进窗体；夹紧从只处理 sel[0] 改为整组。
2. **拖动期间禁整窗精绘**：g_canvasFastDrag 不再要求"无壁纸"——整窗 paint 18ms，
   混进来一帧就是一次顿挫；壁纸是静态底图，拖动期间先不叠，松手补一帧整窗。
3. **GDI 批次即时提交**：上屏 BitBlt 后补一次 GdiFlush()，消除 GDI 批量提交
   造成的"晚一两帧才动"；离屏位图多留 1.5 倍余量，避免甩动时反复重建。
4. **热路径日志开销**：drag_log_on() 缓存 getenv 结果，没开日志时不再每帧 sprintf。

验证：--dpi 150 截图，用户名/密码/按钮对齐正常、窗体边界清晰；
用户实测反馈"这次对了，丝滑的很"。
