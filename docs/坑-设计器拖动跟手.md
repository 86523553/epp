# 坑：设计器里拖组件「跟不上鼠标 / 不丝滑 / 拖到某处拖不动」

> 2026-11-09 结案。这个坑**连续踩了五轮**，前四轮都在改渲染，全部无效。
> 以后再遇到「拖动不跟手」，**先读这一页**，别再从头调渲染。
> 一句话结论：**不是画得慢，是坐标换算错了。**

---

## 一、用户看到的现象（原话）

| 说法 | 实际含义 |
|---|---|
| 「拖动特别慢，易语言拖放很丝滑」 | 控件位移量小于鼠标位移量，越拖差距越大 |
| 「鼠标都跑好远呢，跟拖放还不同步」 | 同上，且是**比例性**落后，不是延迟 |
| 「拖到某个位置之后就无法再向右拖动」 | 边界夹紧写在了拖动过程里 |
| 「框选几个一起拖，只有一个跟着走」 | 多选拖动只处理了 `sel[0]` |
| 「影子方案好一点，但还是不行」 | 渲染路径确实有优化空间，但治不了根因 |

---

## 二、根因（唯一真凶）：位置和尺寸用了两套缩放系数

`ctl_rect()` 旧实现：

```cpp
// 位置：只乘设计缩放 zoom
float x = g_formX + c.x * z;
// 尺寸：走 R()，R() 里又乘一次 g_s（DPI×界面缩放）→ 等于 zoom * g_s
return R(x / g_s, y / g_s, c.w * z, c.h * z);
```

后果（本机 `AppliedDPI=144`，即 150% 缩放，`g_s = 1.5`）：

1. **显示错位**：窗体按 `zoom*g_s` 画，控件按 `zoom` 排 → 越往右下偏得越远；
2. **拖动必然落后**：鼠标走 1px，设计位移只有 `1/g_s = 0.67px`，控件只走 0.67px。
   拖得越快、累计误差越大，而且**永远追不上**——因为每帧都在按错误比例换算。

现在：`float k = g_a.zoom * g_s;` 位置/尺寸/标题条偏移**全用 k**。

> 为什么前四轮查不出来：**100% 缩放下 `g_s = 1`，这个 bug 完全不可见**。
> 所有离线自验都跑在 `g_s = 1`，一直"通过"。见 `pitfalls.md` G3。

## 三、五轮过程（记录走过的弯路，避免重走）

| 轮次 | 当时的判断 | 做了什么 | 结果 |
|---|---|---|---|
| 1 | 每帧整窗重绘 + 脏区越滚越大 | 底图缓存 + 脏矩形（上一帧∪这一帧） | 残影没了，仍慢 |
| 2 | DWM 呈现不可控，移动窗口比画慢一拍 | 分层窗口影子（`WS_EX_LAYERED` + `UpdateLayeredWindow` + `SetWindowPos`） | 好一点，仍不同步 |
| 3 | 位移被逐步截断 | 绝对定位（`dragFrom0 / dragX0 / dragY0`，浮点不累加） | 好一点 |
| 4 | 文献说"要画不要移窗口" | 改回直接 BitBlt 上屏（WinForms AdornerWindow / ImageList_Drag 同款） | 好一点 |
| 5 | **分段计时，先量再改** | 测出整窗 18.9ms、画布 0.34ms、单控件 0.07ms → 绘制不是瓶颈 → 回头查坐标 | **根因命中，丝滑** |

**教训**：用户说「慢」时，先量「一帧各段耗时」。绘制 0.07ms 却感觉慢，
说明问题不在画，而在**算**。

## 四、伴生的四个 bug（同一个症状群，一起修才彻底）

| # | 问题 | 症状 | 修法 |
|---|---|---|---|
| 1 | 拖动过程每帧把位移夹进窗体边界 | 「拖到某处就拖不动了」，鼠标还在走 | 拖动中 1:1 自由跟随（可拖出窗体），**松手时**才吸网点 + 收进窗体（`on_lbutton_up`） |
| 2 | 拖动用的是消息里的过期坐标 | 快速甩动时差几十像素 | 吸空队列后 `GetCursorPos + ScreenToClient` 取光标真值 |
| 3 | 拖动期间混进整窗精绘（18.9ms） | 一帧顿挫 | `g_canvasFastDrag` 在拖动期恒为真，只画画布；壁纸等松手补一帧 |
| 4 | 多选只动 `sel[0]` | 「只有一个跟着走」 | 按下时 `dragSnapCtl` 快照 + 整组同一总位移，按包围盒一起夹 |
| 5 | GDI 批量提交 | 「晚一两帧才动」 | 上屏 BitBlt 后 `GdiFlush()` |

## 五、现行实现（关键符号，改动前先看这些）

| 符号 | 作用 |
|---|---|
| `ctl_rect(const Ctl&)` | 设计坐标 → 屏幕矩形。**位置/尺寸必须同一个 k = `zoom * g_s`** |
| `form_rect()` | 窗体矩形；`cw/ch` 是设计单位，经 `R()` 乘 `g_s` |
| `g_formX / g_formY` | 窗体左上角的**像素**坐标（不再除 `g_s`） |
| `on_mouse_move()` | `DMove/DResize` 分支：绝对定位 + 整组位移 + 对齐吸附 |
| `drag_dirty_frame/add()` | 每帧脏区 = 上一帧 ∪ 这一帧，裁到画布内 |
| `cvs_base_capture()` | 抓「不含被拖控件」的画布底图（开头必须 `GdiFlush()`） |
| `drag_paint_screen()` | 拖动时贴底图 + 补画控件，**直接上屏**，不走 `InvalidateRect` / `WM_PAINT` |
| `g_canvasFastDrag` | 拖动期只重画画布的开关 |
| `g_ghostArmed / ghost_*` | 影子窗口路线，**默认关闭**，仅 `IDE_DRAG_GHOST=1` 时作为对照 |

## 六、下次怎么定位（不要靠猜）

1. **先量**：`IDE_BENCH_DRAG=1 IDE_DRAG_LOG=<绝对路径>`，看 `BENCH` 行。
   GUI 程序没有 stderr，日志必须写文件，且路径要能被进程访问。
2. **再复现缩放**：自验一律带 `--dpi 150`（`g_s=1.5`）跑一遍，再和 100% 比。
   只在 100% 下"通过"的结论一律不算。
3. **看比例**：让控件随鼠标走 100px，量控件实际走了多少像素。
   - **按比例落后**（100px → 67px）＝ 坐标系数错，查 `ctl_rect` 一类换算；
   - **等量但滞后几帧** ＝ 呈现路径问题，查 `drag_paint_screen` / 影子窗口；
   - **一帧顿挫** ＝ 有整窗重绘混进拖动帧，查 `g_canvasFastDrag`。
4. **随手记**：`IDE_DRAG_LOG` 里有 `START / DIRECT / CLAMP / NO_BASE` 等打点。

## 七、写坐标换算时的硬规则（贴墙）

1. **位置和尺寸必须同一个系数**。`zoom` 是设计缩放，`g_s` 是 DPI×界面缩放，
   两者一起乘，谁都不能漏。
2. **不要让 `R()` 和手写乘法混用**：`R()` 内部会乘 `g_s`，
   所以传进去的量必须是 **DIP**；已经乘过 `g_s` 的像素值不要再进 `R()`。
   （`rcStatus` 那里踩过：写成 `S(y / g_s)` = 把 DIP 当像素。）
3. **拖动用绝对定位**：`c.x = dragX0 + (mx - dragFrom0.x) / k`。
   绝不写 `c.x += dx` 后再把 `dragFrom` 改成当前点——除以缩放的小数部分会被逐帧吃掉。
4. **拖动过程不要夹紧**，只在松手时统一收边。
5. **拖动帧里禁止整窗精绘**（实测 18~19ms，一次就是肉眼可见的顿挫）。
