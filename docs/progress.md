## 2026-11-08 打开 .e 卡死问题：定位与修复

### 现象
打开易语言源码有时卡死、有时能打开。

### 实测证据
| 对象 | 结果 |
|---|---|
| 同一条 `e-packager unpack` 连续跑 4 次 | 4.26s / **12.05s** / 0.95s / `--help` 0.97s |
| e-packager 自己的日志 | 真正解包只花 250 ms，其余全在进程启动/加载 `易语言安装目录\lib\krnln.fne` |
| IDE 打开冷/热 | 13.45s（重解包） / 0.20s（走缓存） |

### 根因两条
1. `e_unpack_run()` 的等待循环是 `for (;;)`，**没有超时**——e-packager 只要不退出，IDE 永远不返回，界面泵着消息但业务卡住 = 看到的就是"卡死"。
2. 解包缓存按 `.e` 的修改时间判断，`e` 文件一改就失效；而缓存在/不在对应 0.2s 与 12s 两个极端，表现成"有时能开有时卡"。

### 修复
| 改动 | 目的 |
|---|---|
| 硬超时 120 秒 + `TerminateProcess` | 卡住时到点结束并报错，绝不无限等 |
| 等待期间每秒 `flash("正在解包… N 秒")` | 慢的时候用户能看见进度 |
| 解包前后 `log_add`（含毫秒） | 下次定位直接看输出面板 |
| 启动前 `taskkill /F /IM e-packager.exe` | 清掉上次崩溃残留的实例（两个实例写同一目录会互锁） |
| `e_prewarm()`：启动时异步跑 `e-packager --help` | 让系统缓存/杀软扫描先做完，首次解包不再干等 |
| **默认不用缓存**（用户明确要求：`.e` 会更新，缓存会读到旧内容） | 每次打开都删旧目录重新解包；要秒开可手动加 `ide.ini [ui] unpack_cache=1` |

### 修复后实测
| 次 | 用时 | 解包目录更新时间 |
|---|---|---|
| 第一次 | 2.22 s | 18:54:11（重建） |
| 第二次 | 1.21 s | 18:54:14（重建） |

两次时间戳都变 = 确实每次重新解包；预热把 12 秒压到 1~2 秒。

### 2026-11-08 第二轮：真正根因（窗口关了进程还在 / 看起来卡死）

现场取证：`ide_wiz` 进程活着，但 `EnumWindows` 显示它只剩 `GDI+ Window` 和 `Default IME` 两个隐藏窗口，
主窗口已被销毁 → 用户看到「卡死，关也关不掉，只能任务栏右键关」。

机制（三处叠加，已全部修）：
| # | 位置 | 问题 | 修法 |
|---|---|---|---|
| 1 | `e_unpack_run()` 等待循环 | 等待 e-packager 时一边泵消息，`WM_QUIT` 被内层 `PeekMessage` **吃掉** → 主循环永远等不到退出 → 窗口销毁、进程赖着 | 识别 `WM_QUIT` 后标记 `quitHit` 并立即跳出 |
| 2 | 同上 | 第一版改法「重投 WM_QUIT 后继续循环」→ 队列里永远有它 → **死自旋**，还是关不掉 | 标记后直接跳出外层循环，不再继续等 |
| 3 | `WM_CLOSE` 处理 | 关窗只置标志，要等解包结束才生效 | 进 `WM_CLOSE` 第一行就 `g_a.quit = true`；解包中止分支里若 `g_a.quit` 直接 `ExitProcess(0)`（用户要求：关掉就结束主进程） |

|---|---|

| 启动向导页点关闭 | **0.5 秒内退出，退出码 0** ✔ |
| 关闭后遗留进程 | **0 个** ✔ |
| 打开 `.e` 两次 | 0.62 s / 1.18 s，退出码 0 ✔ |

另外这一轮撤掉了上一轮的两个自作聪明：**启动预热 e-packager**（会和正在解包的进程打架）和 **taskkill 清残留**（可能误杀），

## 2026-11-08 · 打开 .e 假死（真根因）+ 打开速度优化

### 真根因（不是 e-packager）
用户在向导里选完 .e 就"卡住、关不掉"。实测证据：
- `ide.exe` CPU 每秒消耗 ≈1.2s（满核空转），而 `e-packager` 进程早已退出
- `环境\logs\ide.log` 只写了"已启动 e-packager pid=…"，始终没有"解包结束"

两处代码合起来造成假死：
1. `MsgWaitForMultipleObjects(1, &pi.hProcess, FALSE, 200, QS_ALLINPUT)`：文件对话框的
   Shell 扩展线程会留下**取不掉的跨线程消息**，`PeekMessage` 拿不到，但 `QS_ALLINPUT`
   一直报"有输入" → 每轮都 `continue`，**永远走不到检查子进程那一步**。
2. `TIMER_WIZ_GLOW` 每 **50ms** `InvalidateRect(hwnd, NULL, …)`（4K 全窗 GDI+ 重绘）：
   解包期间向导还开着，重绘消息把消息队列一直填满，进一步保证"永远有输入"。

结果：子进程早结束，主进程在爬消息里空转；超时/退出检查都在走不到的分支里，
所以既不会结束也不会响应关闭。

### 修法
- 等待循环每轮**先** `WaitForSingleObject(pi.hProcess, 0)` 查进程，再泵消息，且泵消息上限 200 条
- 解包/编译期间（`g_eBusy`）与窗口最小化时不跑封面动画
- 封面动画 50ms → 100ms（10fps 对雪/星/粒子足够）

### 速度优化（用户选 A+B）
- **A 按 `.e` 内容签名复用**：签名 = 文件大小 + 最后写入时间，写进 `unpack\<工程>\.esig`。
  文件没改动 → 跳过整个 e-packager 调用。实测解包步骤 **469ms → 16ms**（进程总耗时 579→113ms）。
  文件一改签名必变 → 不会读到旧内容（用户"不要缓存"的诉求仍然成立）。
  强制每次都解：`ide.ini [ui] unpack_reuse=0`
- **B 后台线程解包**：向导选完文件后 `CreateThread` 解包，界面立刻可响应；
  解完 `PostMessage(WM_APP_IMPORT_DONE)` 回 UI 线程装填（解析只 20~30ms）。
  命令行/截图验证仍走同步路径，保证返回时数据已就绪。

### 耗时构成（实测）
| 阶段 | 用时 |
|---|---|
| e-packager 进程启动 + 加载 `易语言安装目录\lib\krnln.fne`(16MB) | ~400ms |
| e-packager 真正解包（其自身日志） | 24~250ms |
| 我们的解析（工程/窗口/程序集） | 20~30ms |
| 复用命中后（第二次打开同一未改动的 .e） | 16ms |
